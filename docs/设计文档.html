时刻（Moments）· iOS 全时录音转写 App 设计文档

项目代号 Moments ｜ Bundle ID com.xfish.moments ｜ 版本 v1.3（新增 M1 录音内核详细设计） ｜ 日期 2026-09-22 ｜ 目标设备 iPhone 17 Pro Max ／ iPhone 17（均 iOS 26）｜ 分发：未签名 ipa + USB 侧载 ｜ 形态：两种录制模式（环境 / 会议）→ 后台常驻录音 → 离线转写 → 说话人分离 → 多语言输出 → 辅助语言学习

一句话定义：在 iPhone 上实现一个「点一下就一直在录」的随身语音记录器 —— 锁屏、切 App 都不中断，全程纯离线（无任何网络请求、无服务器、无 API 费用）把周围说话人的声音转成文字、区分「谁在说」、翻成任意目标语言，并把真实录音变成可跟读、可收藏生词的语言学习材料。

1. 项目概述

1.1 目标（Goals）

  • 全时录音：用户手动点「开始」后，App 在前台、后台、锁屏三种状态下持续录音，直到用户主动停止
  • 纯离线转写：不联任何云端服务，音频不出手机。识别引擎本地运行（whisper.cpp）
  • 两遍转写：低延迟的「实时稿」保证当场可见；高精度的「终稿」在设备空闲/充电时补跑
  • 噪声抑制：原始轨 + 降噪轨双路处理，可随时对照与开关
  • 说话人分离 + 声纹库：自动区分「说话人 1/2/3」，用户命名后写入声纹库，后续录音自动认出同一个人
  • 可检索、可回听：全文检索命中后点句子即跳到对应音频位置播放
  • 多语言输出：转写文字可翻成多种目标语言，界面内自由切换，全部在端侧完成（离线翻译）
  • 辅助语言学习：逐句原文/译文对照、点句回听、慢速朗读、跟读比对、生词提取与生词本
  • 零运行成本：无后端服务、无订阅、无按分钟计费

1.2 非目标（Non-Goals）

  • 不做隐蔽录音。系统录音指示器不可隐藏，产品定位是「个人记录助手」而非「采集设备」（见 3.4）
  • 不做跨设备组网采集（多台设备同时开麦汇总）—— 第三方 App 无法读取其他设备的麦克风流
  • 不做云端同步 / 多端共享（v1 只在本机；是否接 iCloud 备份见 15）
  • 不做实时通话转录（接打电话时无法录音，见 3.3）
  • 不做 Android / Mac 版本（Mac 版作为后续可能，可复用核心模块）
  • 不做自动摘要 / 待办提取（需挂 LLM，列为 v2）
  • 不做实时同声传译。v1 的翻译发生在转写完成之后，不是边听边译（实时翻译列入 v2 评估，见 7.1）
  • 不做云端翻译服务。与"纯离线"定位冲突；架构上保留可插拔接口但默认不启用（见 7.4）
  • 不做完整语言课程。不含分级课程、考试题库、语法教学体系；只做「把真实录音变成学习材料」这一件事（见 8.1）
  • 不做电话通话录音。iOS 不提供通话录音 API，不是取舍问题而是能力缺失（见 1.3 事实八）
  • 不做屏幕内容的保存与回看。系统内录路径会经过屏幕录制通道，但屏幕视频一律丢弃、不落盘（见 4.6）

1.3 必须接受的平台事实（Platform Constraints）

事实一：系统禁止静默开麦。iOS 不允许 App 在没有用户交互的情况下自行启动麦克风。因此「随时能录」的准确含义是：用户点一次「开始」之后才进入全时录制。不存在「开机自动录」「进入某地点自动录」这类能力。

事实二：录音指示器不可隐藏。只要有 App 在采集麦克风，iOS 就会在灵动岛 / 状态栏显示指示点，锁屏界面也会提示「某 App 正在使用麦克风」。这是系统级行为，App 层无 API 可屏蔽 —— 这也是本产品不能定位为「隐蔽采集」的根本原因。

事实三：后台可继续录音，但会被中断。配置 UIBackgroundModes = audio 后，录音本身就是合法的后台执行理由，锁屏不会挂起进程（这一点比「播放静音音频保活」的取巧方案更正当、更稳）。但来电、Siri、其他 App 抢占音频会话时会被强制打断，必须实现自动恢复（见 3.3）。

事实四：蜂窝网络下载安装包上限 200 MB。超过该体积的 App，用户必须连 Wi-Fi 才能下载安装。本项目仅模型就远超此限，因此模型不打包进 ipa，改为首次启动时按需下载（见 12.2）。

事实五：Whisper 的翻译任务只能翻成英文。Whisper 内置的 translate 任务等价于「任意语言 → 英文」，不能直接翻成中文、日文、法文等；transcribe 任务则只在原语言内输出文本。

这意味着「多语言输出」不可能靠识别引擎顺带完成，必须单独设计一个翻译层（translation layer）—— 见第 7 章。

事实六：端侧翻译的质量明显低于云端。离线翻译模型体积受限，在口语、俚语、长难句、领域术语上会明显劣于云端服务；且系统翻译框架支持的语言对是有限的。

这不是能绕开的技术问题，而是必须在产品设计上消化的取舍 —— 对策是"原文永远可见、译文可修正"，而不是宣称译文准确（见 7.4）。

另有两个次要但真实存在的限制：低电量模式（Low Power Mode）会限制后台活动与网络，可能影响后台转写；热控（thermal throttling）在长时间高负载推理后会让系统降频，需主动降档（见 10.4）。

事实七：麦克风是独占资源，无法录「其他 App 正在使用的麦克风输入」。同一时刻只有一个 App 能持有麦克风输入流；其他 App 采集到的音频数据对本 App完全不可见，iOS 不提供任何 API（越狱除外）。我们能知道"别人在用麦"（因为会被中断，见 3.3），但拿不到数据。

因此「录所有使用麦克风的语音」这一诉求，指的是"别人开麦时我也能录"那部分是做不到的。（见 4.6 可行性分层）

事实八：能录「其他 App 播放出来的声音」（系统内录），也能录电话？—— 前者可以，后者不行。

系统内录（system audio capture）可行：通过 ReplayKit 的广播上传扩展（Broadcast Upload Extension），可拿到其他 App 的音频输出 —— 在线会议对方的声音、视频、播客都能录到。

电话通话录音不可行：iOS 不提供通话录音 API，任何声称能录电话的 App 都是借助三方通话服务绕道实现的。这一条必须让用户明确知道。（见 4.6）

3. 运行形态与平台约束

3.1 目标形态：一键开始，之后一直录

用户点击「开始」
   ↓
[持续录音] ── 前台 ─┐
   ↓               ├── 均不中断
[持续录音] ── 后台 ─┤
   ↓               │
[持续录音] ── 锁屏 ─┘
   ↓
用户点击「停止」→ 进入终稿转写与说话人归属

整个过程不设时长上限。为防止极端情况（忘记停止导致录满存储），提供两道保险：单次录音时长上限（默认 12 小时，可调）与剩余磁盘空间阈值（低于 1 GB 自动停止并保留已录内容）。

3.2 后台执行与保活机制

机制配置说明
后台模式声明Info.plist 中 UIBackgroundModes = audio必要前置。录音本身即构成合法的后台执行理由
音频会话类别AVAudioSession.Category.record（或 .playAndRecord，以便降噪/回放共存）决定被打断时的行为、是否静音、以及能否混音
与播放共存options: [.mixWithOthers]不打断用户正在听的音乐（代价：录音中可能混入外放声音，需在设置里说明）
保活冗余不需要额外手段与既有项目不同：录音会话本身即是后台执行权来源，无需"播放静音 PCM"这类取巧做法
低电量模式监听 ProcessInfo.isLowPowerModeEnabled开启时暂停实时转写（保留录音），避免被系统判定为高耗电而杀死

3.3 中断与恢复（本项目最大风险点）

音频会话被打断是必然事件，不是异常。必须在打断结束后自动恢复录音，并且保证时间轴连续（用户不应该在结果里看到一段无声的黑洞）。

中断来源系统行为本项目对策
来电 / 微信语音 / 视频通话会话被打断，录音被系统停掉监听 AVAudioSession.interruptionNotification；.began 时标记断点并落盘当前分片，.ended 且 shouldResume 为真时自动重启录音，断口写入时间轴
Siri 被唤起同上同上（.ended 后自动恢复）
其他 App 抢占（如录音类 App）本 App 会话被强制释放同上；若恢复失败，进入退避重试（1s / 2s / 5s / 10s，上限 10 次）
AirPods 摘下 / 蓝牙断开触发路由变更，输入设备切换监听 routeChangeNotification；切换后重建输入节点（AVAudioEngine 在设备变更后常需重连）
耳机插入 / 拔出同上同上
系统内存压力App 可能被系统回收分片滚动落盘（见 4.3）把损失限制在单个分片；重启后用 recoveryState 续录并补一条时间轴断口记录
设计原则：录音通路的健壮性优先于一切其他功能。录音层不允许因为"转写线程忙"而丢音频 —— 采集（capture）与转写（transcription）必须解耦，中间用有界队列缓冲，队列满时丢转写任务而不丢音频。这与既有项目「行情自愈」的经验一致：宁可降级功能，不能让主干断掉。

3.4 录音指示器的产品含义

录制期间锁屏与状态栏会持续显示麦克风指示。这不是缺陷，而应被产品设计主动利用：锁屏界面与灵动岛即是「正在记录」的天然状态展示，用户一眼可知是否在录。UI 上无需再重复强调，但必须在首次使用时明确告知——这是合规要求，也是尊重被录音方的起点。

合规提示（产品层，非技术层）：录音涉及他人声音，需遵守当地法律与他人知情权。建议在设置页明确提示「请确保已获得在场人员同意」，并在 App 图标/名称上不做任何暗示隐蔽性的表述。此条目属于产品决策，需用户自行把握适用场景。

4.2 双轨处理架构

麦克风 (16 kHz / mono / PCM)
        │
        ├──────────────▶ [原始轨 raw] ────┬──▶ 落盘（Opus）
        │                                └──▶ 终稿转写（whisper small）
        │
        └──▶ [GTCRN 降噪] ──▶ [降噪轨 enhanced] ──┬──▶ 实时转写（whisper base）
                                                 └──▶ 内存环形缓冲（默认不落盘）

双轨的意义不是"存两份"，而是让两条处理链可以独立切换与对比：

  • 实时字幕走降噪轨 —— 用户视觉上更干净，且降低 Whisper 在噪声上的幻觉（hallucination，模型在无语音处凭空生成文字）概率
  • 终稿转写走原始轨 —— 保留全部细节，避免降噪伪影损伤识别
  • 设置页提供「降噪 开/关」与「终稿用哪条轨」两个开关，默认值由真机 A/B 实测确定（见 M3 验收标准）

4.4 编码与容量估算

修正一（已修正）：前一版方案沟通中给出的「16 kHz 单声道 PCM 约 68 MB/小时」是算错的。正确值为 16000 采样 × 2 字节 × 3600 秒 ≈ 110 MB/小时。
修正二（本版修正，重要）：原方案选定 Opus 作为落盘编码，经核实这是一个站不住的选择 —— Opus 在 Apple 音频栈中主要以解码形态存在（服务于 FaceTime、HLS 等场景），而 AVFoundation 的编码路径（AVAudioFile / ExtAudioFile）能否输出 Opus 并不确定；要确保可用就必须引入第三方 libopus，为省 5 MB 存储而增加一个 C 依赖与编译复杂度，不划算。

结论：改为 AAC（.m4a，AAC-LC）。它系统原生、确定可用、体积与 Opus 相当（同为 16 kHz 单声道，32 kbps 下每小时约 14 MB），且零第三方依赖。Opus 降级为"待实测的备选项"，不作为首版依赖。

AAC 相比未压缩 PCM 省约 8 倍，且是为语音设计的成熟编码，对识别精度的影响可忽略（需在 M2 实测确认）。压缩在后台队列执行，不阻塞采集线程。

一个必须补偿的实现细节：AAC 编码器自带编码器启动延迟（encoder priming / delay），每个文件开头的样本数与源并不严格对齐（通常约两千余采样点）。因为我们是每 60 秒切一个新文件，这会累积成数十毫秒级的跨片时间戳偏差。

对策：在写入分片元数据时记录该片的实际样本总数与编码器延迟，用样本计数而非墙钟时间来计算 start_ms / end_ms —— 让时间轴由样本数推导，而不是由系统时间戳相减推导。这样偏差不会累积。（见 4.11）

录其他 App 播放出来的声音

优势二 「我（audioMic）」与「对方（audioApp）」在数据层天然分成两路，说话人分离的难度大幅下降（少了一路需要聚类的对象）

约束四：开销屏幕视频即使丢弃，系统仍会采集与编码，带来额外耗电与发热，比纯音频录音重得多
约束五：审查屏幕录制属敏感能力，App 审核趋严，需清晰的用途声明与隐私说明；不得用于采集屏幕内容本身
约束六：合规升级录制通话对方的声音比录制环境声敏感得多，许多地区对通话录音有明确法律规定。必须显著提示并获取在场各方同意（见 R14、R26）

4.8 音频会话配置：独占 vs 共存（M1 关键取舍）

这是"全时录音"里最容易被忽略、但对实际体验影响最大的一个决策，必须先说清楚物理事实。

事实来源
.record 类别下，其他 App 的音频会停止音频会话类别的固有语义：录音类会话不混音
要与其他 App 共存，必须显式设置 mixWithOthersApple 文档：清空该选项并激活会话会中断其他音频会话；设置它才会与后台 App 的音频混音
反过来同样成立：其他 App 激活一个不带混音的会话时，也可能把我们中断会话仲裁是双向的，这不是我们能单方面决定的

两条路线

策略会话配置好处代价
独占录音
Exclusive		 .record（或 .playAndRecord 不带 mixWithOthers） 录音最干净；不会录到本机扬声器外放的声音（无污染） 用户一整天不能听音乐/看视频/听语音消息（会被我们中断）—— 对"全时录音"是灾难级体验
共存录音
Coexistent		 .playAndRecord + .mixWithOthers 用户可正常使用手机，录音可长时间挂着 麦克风会录到本机外放的声音（音频被污染，转写质量下降）；且仍可能被别人的非混音会话抢占
M1 决策：默认「共存录音」，并提供「高保真（独占）」开关。

理由：本项目的核心承诺是"一直录"。如果一开录音就让手机变成砖头（不能听歌看视频），用户第二天就不会再打开它了 —— 录音再干净也没有意义。因此共存是默认真实可用的选择，独占留作正式访谈/会议时的主动选项。

开启共存时的提示文案必须直白：「录音期间可能录到本机外放的声音，建议佩戴耳机」。

顺带一个结论：会议模式（系统内录）天然绕开了这个两难 —— 它直接从 App 的音频输出取数字信号，不需要靠麦克风去"听"扬声器，因此既能让用户正常使用手机，又不会污染音频。这是把系统内录纳入范围的又一个有力理由（见 4.6）。

4.9 采集引擎与实时线程纪律

项设计
采集接口AVAudioEngine + inputNode.installTap(onBus:bufferSize:format:)
缓冲大小候选 1024 / 2048 / 4096 帧；由实测决定（延迟 vs 回调频率的平衡）。回调过于频繁会增加实时线程负担，过大会增加延迟
转换链采集 → （可选）降噪 → VAD → 编码落盘 / 转写，各环节在不同队列上，用环形缓冲解耦

实时线程纪律（硬约束）：installTap 的回调运行在实时音频线程上。在该回调内禁止：分配内存、加锁（DispatchQueue.sync / NSLock）、做文件或网络 I/O、调用任何可能阻塞的 API、触发 ARC 的重活。

违反的后果不是"报错"，而是偶发的音频丢帧与爆音 —— 数据听起来还在，实际已经有空洞。这类问题几乎无法事后定位，只能靠结构上避免。

正确做法：进入回调前预分配一个环形缓冲（ring buffer）；回调内只做 memcpy 与原子指针更新；消费者在后台串行队列上取出处理。

M1 里最容易写出"看起来能跑、实际偶发丢帧"的地方就在这里。因此 M1 的第一步不是拼功能，而是先把这个采集管道与环形缓冲做对，再用长时间实测验证是否有丢帧（靠样本计数校验，见 4.11）。

4.10 采样率与格式转换

设备硬件原生采样率通常是 48 kHz（且会随路由变化，插耳机/连蓝牙后可能改变），而识别与落盘统一用 16 kHz 单声道。

路线做法优点缺点
A. 直接以 16 kHz 采集给 installTap 传 16 kHz 的格式，交由系统转换代码最少采样率转换（SRC）在音频线程内不透明地完成，出问题无法观测，也难以插入降噪
B. 原生格式采集 + 显式转换（选定）以原生格式（如 48 kHz）采集，后台队列用 AVAudioConverter 转 16 kHz可控、可观测、可插入降噪；转换参数明确多一步、需自行处理转换失败与格式不匹配

选择 B 的理由：本项目要在同一路音频上做降噪、VAD、落盘、转写四件事，对格式与采样率的可控性比省几行代码重要得多。

必须记日志的两项：实际采集格式（采样率、声道数、位深）与转换后的输出格式。原因是"采样率不匹配导致音调怪异/速度不对"是这类项目最经典的坑，而它只有在锁屏、插耳机、换蓝牙之后才会暴露 —— 不记录现场就等于放弃定位能力。

4.12 中断与恢复实现

中断是必然事件而不是异常。实现上必须把"可能被打断"当作常态来设计。

事件源含义处理
AVAudioSession.interruptionNotification会话被抢占（来电、Siri、其他 App）.began：finalize 当前分片、置 interrupted；.ended 且 shouldResume：进入 recovering 并重启引擎
AVAudioEngineConfigurationChange系统重建了音频图（设备变化等）必须停止 → 重建引擎 → 重启。这是"静默停录"最常见的原因，最容易被漏掉
AVAudioSession.routeChangeNotification输入设备切换（拔插耳机、蓝牙连断）重建输入节点与格式转换器；重新记录实际采集格式
AVAudioSession.mediaServicesWereResetNotification媒体服务被系统重置（音频栈已失效）会话与引擎全部重建，不复用任何旧对象
前后台切换通知进入后台 / 回到前台回到前台时主动做一次健康度校验（不信任"应该还在录"）
系统内存警告App 可能被回收立即 finalize 当前分片，缩短损失窗口

恢复退避策略

立即重试 1 次  →  1s  →  2s  →  5s  →  10s  →  10s  …（上限 10 次）
      任一次成功 → 归零计数，回到 recording，并记一条断口
      全部失败   → failed（finalize 已录内容 + 明确告知用户）

断口（Gap）的记录方式

恢复后新分片的 start_ms 仍由样本累计推导，因此中断期间的时间会自动体现为"上一片 end_ms 与下一片 start_ms 之间的间隔"。断口不需要额外机制去"制造"，只需要在 UI 上把它显式标注出来（见 11.3）。

App 被强杀后的恢复

步骤做法
录音开始时写入一条"活跃会话"标记（state = recording）
正常停止时标记改为 done
App 启动时若发现存在 state = recording 的会话、但当前并未在录音 → 判定为异常终止 → 提示用户"上次录音异常结束"，并提供查看/标记完成/继续录制
这一条是"无调试器"环境下的关键诊断入口。因为没有崩溃日志的实时访问能力，App 自己识别"我上次是异常死的"并提供入口，是唯一能让用户把问题反馈清楚的方式。

停滞看门狗（Stall Watchdog）

中断通知覆盖的是"系统明确告知我们被打断"的情况。但还有一类更危险的情形：系统没有报任何错，音频却已经不来了（连接半死式的静默失效）。因此需要独立的看门狗兜底。

项设计
判定依据记录 lastFrameAt（最后一帧音频的到达时刻）；定时器每秒检查，若 now − lastFrameAt > 3 秒 且状态为 recording → 判定停滞

5. 转写引擎（whisper.cpp）

5.1 两遍转写（Two-Pass）

录音进行中  ──▶ ① 实时稿：whisper base（量化），滑窗转写当前片段，秒级可见
                        ↓ 结果直接展示，但会被后续重解不断修正
录音结束后 / 充电+息屏 ──▶ ② 终稿：whisper small（量化），整片重转
                        ↓ 覆盖式写入，与实时稿并存可对照
遍次模型触发条件目标可关闭
实时稿base（q5 量化）录音中，VAD 判定有语音当场可读，秒级延迟是（省电档）

这个设计的价值在于把「耗电」与「准确」解耦：用户白天可以关掉实时转写换取整日续航，晚上插上充电器再一次性出准确结果；录制本身从不中断。

5.2 滑窗与自我修正（为什么会"回改"）

Whisper 是批式（batch）模型，不是流式（streaming）模型——它的输入是「一段完整音频」，输出是「一段完整文字」。要做实时字幕，只能自己搭"边录边重解"的循环：

当 VAD 判定进入语音段：
  每积累 step（例如 0.5s）：
     取 [段起点, 当前时刻] 的音频 ──▶ Whisper ──▶ 覆盖式替换屏幕上该段的文字
     条件：保留 last 若干词做上下文（滑窗重叠），避免断句断裂

必须提前接受的现象：字幕会先出现再被修正（前几秒的错字在 1~2 秒后被改对）。这不是 bug，是离线批式模型的固有特性。UI 上应把"正在识别中"的片段做视觉区分（如浅色/斜体），避免用户以为文字在乱跳。

同时它是 Whisper 的幻觉（hallucination）高发场景：安静无声处可能凭空生成「谢谢观看」「字幕由 xx 提供」之类的句子。对策：① VAD 严格把关，非语音段不送模型；② 对高重复文本做黑名单过滤；③ 若无语音活动则输出空。

  • ipa 内不含模型，安装包保持在小体积（预计 < 20 MB，主要来自 sherpa-onnx 与 onnxruntime 的 framework）
  • 首次进入录音页时引导下载：base 必选（~57 MB），small 推荐（~181 MB）
  • 下载源需为可稳定访问的地址（GitHub Releases / 自有对象存储），需支持断点续传与校验（sha256）
  • 模型存放在 Application Support/Models/，可被系统清理策略影响，需检查存在性并重新下载
  • 设置页可查看模型占用并单独删除

5.6 备选方案（备而不用）

由于 sherpa-onnx 已在技术栈内，其自带的 SenseVoice 模型是一个零增量成本的备选（同属离线、中文与粤语表现更强、非自回归因而速度更快）。若 M2 实测发现 whisper small 的中文准确率或速度不达标，可直接在 sherpa-onnx 内切换，无需引入新依赖。保持该后路是选 sherpa-onnx 而非自研语音处理的一个重要附带收益。

6. 语音处理（sherpa-onnx）

6.1 VAD 语音活动检测（Voice Activity Detection）

项设计
作用切出"有人说话"的片段。它是整个链路的闸门：只把语音送进转写与声纹，既省电又抑制幻觉
实现sherpa-onnx 内置的 VAD（Silero / TEN-VAD 类），16 kHz 输入，逐帧判定
参数起始静音阈值、结束静音时长（尾静音，例如 0.5s 判定一句结束）、最短语音时长（过滤咳嗽等短促噪声）
输出语音段列表 [{start_ms, end_ms}]，作为后续所有处理的基本单元
调参要求尾静音过短会切碎句子、过长会延迟实时字幕。默认值需真机实测后确定

6.2 GTCRN 降噪（Speech Enhancement）

GTCRN（Global Token Channel Attention Recurrent Network）是 sherpa-onnx 内置的语音增强模型，用于从含噪音频中估计并压制背景噪声。

项设计
处理位置采集后立即处理，产出降噪轨（见 4.2 双轨架构）
落盘默认不落盘（可由原始轨随时重算）；仅 A/B 实测期可临时开启留档
可切换设置页开关；实时字幕轨与终稿轨的选择相互独立
对比方式对同一段原始音频分别用原始轨/降噪轨跑一遍 whisper small，比较字错误率（WER, Word Error Rate）与人工可读性

反直觉但重要：降噪并不必然提升识别准确率。降噪算法会引入失真伪影（artifact / musical noise），而 Whisper 这类在大规模含噪数据上训练的模型本身已具备较强抗噪能力——过度降噪可能抹掉模型所需的语音细节，使 WER 反而上升。因此"降噪"在本项目中的定位是「可验证的选项」，而不是「无条件的改进」。这也是双轨架构存在的唯一理由。

① 语音分割 (segmentation)

                                        │
② 声纹提取 (speaker embedding)          ▼

                                        │
③ 聚类 (clustering)                     ▼

                                        │
④ 回填 (labeling)                       ▼

6.5 超长会话的分块与身份对齐

这是全时录音形态带来的特有难题。聚类是批式全局优化：8 小时对话可能包含数万个语音段，一次性聚类在手机上会内存耗尽且耗时不可接受。必须分块处理，再把块与块之间的身份对齐。

把整段会话切成 chunk（例如每 10 分钟一块）
        │
每块独立聚类 ──▶ 块内标签：chunk1 = {A, B}，chunk2 = {P, Q, R}
        │
计算每块的簇质心 ──▶ 与「本会话已确认身份表」及「全局声纹库」比对
        │
        ├── 匹配上 ──▶ 统一为同一身份（speaker linking，跨块身份对齐）
        └── 未匹配 ──▶ 新身份
        │
输出：全会话统一的说话人标签序列
要点设计
块大小10 分钟（可调）。越小越省内存，越大聚类越准（样本多）
跨块对齐以质心向量做比对，而非依赖块内序号（序号在块之间没有意义）
增量处理录音进行中即可对已完成的块做说话人处理，避免停止后一次性等待很久
调度时机与终稿转写同一时机（充电/息屏），避免与录音争抢算力

6.6 已知局限：重叠说话（Overlapping Speech）

当两人及以上同时说话时，说话人分割的准确率会显著下降，容易把两个人的声音混成一段并归给其中一人。这是语音领域的公认难题，不存在"解决"方案，只能降级处理。

策略说明
标注而非隐瞒检测到可能重叠的片段，在 UI 上以「可能多人同时说话」标记，而不是假装判断正确
转写优先重叠段的文字通常仍可正确转出（Whisper 擅长分离混合语音的内容），只是归属不可靠。因此归属不确定时保留文字、把说话人标记为「未知/多人」
不承诺解决设计文档中明确记录为已知边界，避免验收时被当作缺陷

7. 翻译层（Translation）

7.1 翻译在链路中的位置

先明确一条被否掉的捷径：Whisper 自带的 translate 任务只能翻译成英文（任意语言 → 英文），不能翻成中文、日文等其他目标语言。因此翻译必须是转写之后的一个独立阶段，而不是识别的一部分。

录音 ──▶ 转写（whisper，原语言文本）
              │
              ├──▶ [实时稿] 仅原文，不翻译        ← 实时阶段不介入翻译
              │
              └──▶ [终稿] 准确的原文文本
                        │
                        ▼
                   【翻译层】按用户选择的目标语言翻译
                        │
                        ├── 原文 + 译文 双语对照
                        ├── 逐段保留说话人标签与时间戳
                        └── 结果按 (段落, 语言) 缓存到数据库
设计要点说明
输入是文字不是音频翻译的对象是终稿文本。这带来一个关键收益：换语言不需要重跑识别，只需重跑翻译（成本低一个数量级）
不介入实时阶段实时稿本身还在被滑窗不断修正，翻译一个还在变的文本既浪费又会让字幕乱跳。实时翻译列入 v2 评估
保留结构译文挂在转写片段上，因此说话人标签、时间戳、点句回听全部自动继承，不需要额外对齐
逐段独立翻译以 VAD 切出的句级片段为单位，而非整篇长文。段落短 → 翻译质量更好、可并行、可增量

7.2 引擎选型（四条路线对比）

方案模型体积离线优点缺点结论
A. 系统 Translation framework 0（语言包由系统管理） 是 端侧运行、免费、无需自建语言对、由系统维护升级 语言对有限（远少于「翻译 App」宣传的 60+ 语言）；长句与口语质量一般；语言包需用户下载 主用
B. 系统 Foundation Models
（iOS 26 端侧 LLM）		 0（系统内置） 是 免费、无下载；能"理解并解释"，适合生词释义、句子讲解、语法说明 速度慢，不适合大批量翻译；需设备与系统满足 Apple Intelligence 条件；输出不完全可复现 用于讲解，不用于批量翻译
C. 专用 NMT 模型
（OPUS-MT / NLLB 蒸馏，ONNX）		 每个语言对数十 MB 是 可复用已有的 onnxruntime，完全自主可控 语言对零散需分别管理；中文口语与长句质量一般；属于"自己维护一份比不上系统的翻译" 不采用（备选）
D. 本地小 LLM
（Qwen 0.6B~1.7B GGUF，走 llama.cpp）		 约 400 MB ~ 1.1 GB 是 翻译质量最好；一个模型同时可做翻译、生词释义、句子讲解、以及未来的摘要/待办（一套模型解决多件事） 体积大、推理慢、耗电高；llama.cpp 与 whisper.cpp 同属 ggml 生态，集成成本不算高但仍是新增依赖 不采用（保留为升级路径）
云端翻译（DeepL / Google / LLM） — 否 质量最高 与"纯离线、音频/文本不出手机"的核心定位冲突；有费用与联网依赖 不采用

选 A 的核心理由：翻译引擎是四件事里唯一「用系统现成的比自建更好」的部分 —— 零体积、零维护、端侧、免费。把工程预算集中在本项目真正独有的价值上（全时录音、说话人分离、学习材料化），而不是重复造一个翻译系统。

同时注意 B 的存在：iOS 26 的端侧系统模型让"生词释义 / 句子讲解"这类生成式需求也能零成本端侧完成，这直接决定了语言学习层的可行性。

7.3 按需翻译与缓存（核心设计）

用户点「选择语言」→ 选「日文」
        │
        ▼
查询 translations 表：(segment_id, target_lang) 是否已有缓存？
        │
        ├── 命中 ──▶ 立即显示（切换语言秒出）
        │
        └── 未命中 ──▶ 批量翻译该会话的所有段落
                       ├── 显示进度（"已翻 32/180 句"）
                       ├── 结果写回缓存
                       └── 可随时中断，已翻部分保留
设计点说明
不预翻所有语言用户实际只会看一两种语言。预翻 N 种语言 = N 倍算力与存储，全属浪费
缓存键(segment_id, target_lang, engine_version)。带引擎版本是为了在翻译引擎升级后能识别出旧译文可重翻
可中断可续长会话翻译是批量任务，必须能中断、能续、能只翻未完成的段落
执行时机优先放在终稿转写的同一批处理窗口（充电/息屏，见 10.4）；也可在前台立即执行（短会话）
清理译文随会话删除而删除；提供「清理全部译文缓存」入口

7.4 端侧翻译的质量边界与对策

必须向用户诚实：端侧翻译在以下场景会明显失真 —— 口语与俚语、方言口音、长难句、专业术语、人名地名、文化特定表达。这是模型体积受限的必然结果，不是 bug，也无法通过调参消除。

对策说明
双语对照为默认呈现原文永远可见，译文作为辅助。这一点在本项目中还额外成立一个理由：用户要学语言，看原文本身就是目的，不是干扰
术语表（glossary）用户可维护「不翻译的人名/专有名词」列表，翻译前后做保护与还原，避免把人名翻得面目全非
允许手动修正译文可编辑并保存，修正后的结果优先展示（同时也能作为后续质量评估的样本）
语言可用性前置校验选择语言时用 LanguageAvailability 实时查询该语言对是否可用、语言包是否已下载；不可用则明确提示并引导下载，而不是静默失败
可插拔接口翻译层对外只暴露统一协议，云端实现作为预留但默认关闭的选项；用户若未来改变主意只需换实现（见 10.3）

7.5 逐段语言检测（混合语言对话）

现实对话常常中英夹杂。Whisper 会为每个段落输出检测到的语言，因此可以做到逐段判定源语言，而不是给整段录音强加一个语言标签。

场景处理
整段都是中文正常翻译
整段都是英文正常翻译
段内中英混合以该段主语言为源语言翻译，译文保留混杂特征（不强行"纠正"成纯一种语言）
语言置信度低标记为「语言未定」，翻译结果标注不确定性
对语言学习的额外价值：逐段语言检测能直接标出「这段录音里哪几句是外语」，这正是学习者最关心的部分 —— 它可以自动过滤出「值得反复听的目标语言句子」，而不需要用户手工翻找。这一能力见 8.5。

8. 语言学习层（Language Learning）

8.1 设计立场

本项目不做语言课程，只做一件事：把你自己录到的真实语音，变成属于你的学习材料。

这个立场的意义在于划清边界：

  • 不做分级课程、考试题库、语法体系教学 —— 那是教科书和 Duolingo 的领域
  • 要做的是：真实语料 + 逐句对照 + 可回听 + 生词沉淀。真实语料是任何教材都买不到的，而它恰好是你每天都在产生的
  • 因此本层的所有功能都围绕一个动词展开：反复听、逐句看懂、把不会的词留下来

8.2 逐句对照（Sentence Alignment）—— 本项目的先天优势

跨语言的「原文-译文对齐」通常是一件麻烦事（需要专门的句对齐算法）。但本项目天然不需要对齐：

VAD 切出的语音段 = 一个句级单位
      │
      ├──▶ 原文（whisper 转写，绑定 segment_id）
      ├──▶ 译文（翻译这段原文，绑定同一个 segment_id）
      └──▶ 音频（时间区间绑定同一个 segment_id）

三者共用同一个 ID，所以「对齐」在数据模型成立的那一刻就自动成立了。

显示模式（界面可切换）

模式展示适用
原文只显示源语言文本复习母语内容、专注原话
译文只显示目标语言文本快速理解内容
双语对照（默认）原文在上、译文在下，逐句对应语言学习的主场景

8.3 听与跟读

功能实现要点
点句回听复用 9.3 的时间戳回放句子左侧时间戳可点，直接播放对应音频
慢速播放AVAudioPlayer.rate（需 enableRate = true）提供 0.5× / 0.75× / 1×；必须保持音高不变（时间伸缩而不变调），否则听不懂反而更难学
单句循环（AB 复读）手动指定 A/B 点或直接循环当前句语言学习最高频的操作，务必做成一步可达
跟读比对录用户跟读 → 用 已有 whisper 转写 → 与原文比对，给出准确度复用已有引擎，零新增依赖；产出的是文本层面的准确度

必须明确的边界：跟读比对给出的是「你说的内容对不对」（文本比对），不是「你的发音好不好」（音素级发音评分）。真正的发音评分需要音素对齐与韵律分析，属于另一个专业领域，不在本项目范围内。UI 文案必须避免让用户误以为是发音打分。

8.4 朗读（TTS）

项设计
引擎系统 AVSpeechSynthesizer：端侧、免费、多语言、语速可调、零额外依赖
用途一朗读译文 —— 听目标语言的标准发音，同时脱离原文检验自己是否听懂
用途二朗读原文 —— 在嘈杂录音本身听不清时，用合成语音还原句子
用途三连续播放整篇 —— 当作泛听材料
边界系统 TTS 音质不如真人，且语调平淡；因此不能替代原声回听，两者并存（原声练真实听力，TTS 练清晰输入）

8.5 生词提取与生词本

生词判定：查表，不调模型

转写文本
   │
   ├── 分词（英文按空格；中文需分词，用系统 NLTokenizer 或内置分词）
   │
   ├── 词形还原（lemmatization）：buy / bought / buying 归一为 buy
   │      ↑ 不做这一步，同一个词会被当成三个生词，生词本会迅速失去意义
   │
   ├── 查词频表：命中高频表（如 COCA 前 5000 词）内 → 视为「已掌握」
   │             超出高频表 → 标记为「生词」
   │             （再结合用户自选的水平档 A1–C2 调整分数线）
   │
   └── 输出：本会话生词列表（含出现次数、所在句子、时间戳）
为什么不用 LLM 判断生词？因为「这个词是不是高频词」是一个确定性问题，查表更快、更稳、可复现、零能耗。LLM 的生成能力应该用在需要理解和表达的地方（释义、讲解、造句），而不是浪费在查表就能解决的事情上。这个分工原则贯穿整个语言学习层。

生词本

项设计
条目内容词形（原形）、出现次数、首次/最近出现时间、来源录音、上下文句子（原文 + 译文）、可回听片段
自动收集学习模式下标记的生词自动入库，无需手工录入
手动增删可把误判的词移出（"我会了"），也可手动加入（自定义词表）
释义用系统 Foundation Models 端侧生成：结合上下文给出该词在此处的中文意思 + 一个例句。也允许接系统词典
导出导出为 Anki 可导入的 CSV（词形 / 释义 / 例句 / 音频文件名）与 Markdown。是否做见 Q11

8.6 学习模式（界面形态）

在会话详情页增加一个「学习模式」开关，切换后界面重组为学习视图：

区域内容
主区逐句卡片：原文（可隐藏）→ 译文（可隐藏）→ 点听 → 慢速 → 生词高亮
操作一句一循环（上一句 / 下一句 / 复读 / 跟读）
侧区本会话生词列表，点击即跳到所在句子
筛选「只看有生词的句子」「只看目标语言的句子」（依赖 7.5 的逐段语言检测）
退出回到普通阅读视图，学习标记不丢失

8.7 本层明确不做的事

  • 不做 SRS 间隔重复算法（v1 只做生词本 + 手动标记已掌握；SM-2 / FSRS 等算法列入 v2 评估）
  • 不做发音打分（见 8.3 边界说明）
  • 不做语法体系教学与练习题生成
  • 不做社交 / 排行榜 / 打卡（与"个人记录"定位无关）

9. 存储与检索

9.1 数据模型

采用 SQLite（配合 Swift 侧封装库）。所有时间字段一律存 Unix 毫秒（epoch milliseconds），展示时统一按用户本地时区（UTC+8）格式化 —— 不使用无时区的字符串，避免时区偏移导致的判定错误。

-- 会话（一次"点开始到点停止"）
CREATE TABLE sessions (
  id            TEXT PRIMARY KEY,
  title         TEXT,
  started_at    INTEGER NOT NULL,   -- Unix ms
  ended_at      INTEGER,
  duration_ms   INTEGER,
  state         TEXT,               -- recording / paused / done / failed
  has_gap       INTEGER DEFAULT 0,  -- 是否存在中断断口
  note          TEXT
);

-- 音频分片
CREATE TABLE audio_segments (
  id            TEXT PRIMARY KEY,
  session_id    TEXT NOT NULL,
  seq           INTEGER NOT NULL,
  file_path     TEXT NOT NULL,
  start_ms      INTEGER NOT NULL,   -- 相对会话起点
  end_ms        INTEGER NOT NULL,
  codec         TEXT,               -- opus
  bitrate       INTEGER,
  bytes         INTEGER,
  expires_at    INTEGER             -- 清理用；NULL = 永久保留
);

-- 转写片段
CREATE TABLE transcripts (
  id            TEXT PRIMARY KEY,
  session_id    TEXT NOT NULL,
  segment_id    TEXT,               -- 对应音频分片，用于回听
  start_ms      INTEGER NOT NULL,
  end_ms        INTEGER NOT NULL,
  text          TEXT NOT NULL,
  pass          TEXT NOT NULL,      -- realtime / final
  speaker_id    TEXT,               -- NULL = 未归属
  overlap       INTEGER DEFAULT 0,  -- 疑似重叠说话
  confidence    REAL,
  lang          TEXT
);

-- 说话人
CREATE TABLE speakers (
  id            TEXT PRIMARY KEY,
  name          TEXT,               -- NULL = 未命名，显示"说话人 N"
  is_self       INTEGER DEFAULT 0,
  avatar_color  TEXT,
  created_at    INTEGER
);

-- 声纹向量（一人多条）
CREATE TABLE voiceprints (
  id            TEXT PRIMARY KEY,
  speaker_id    TEXT NOT NULL,
  embedding     BLOB NOT NULL,      -- float32 向量原始字节
  dim           INTEGER NOT NULL,
  quality       REAL,               -- 提取质量，用于淘汰劣质向量
  source_session_id TEXT,
  created_at    INTEGER
);

-- 全文索引（外部内容表模式，避免文本重复存储）
CREATE VIRTUAL TABLE transcripts_fts USING fts5(
  text,
  content='transcripts',
  content_rowid='rowid',
  tokenize='trigram'
);

-- 译文（按需翻译的缓存，见 7.3）
CREATE TABLE translations (
  id            TEXT PRIMARY KEY,
  segment_id    TEXT NOT NULL,      -- 对应 transcripts 的一个片段
  session_id    TEXT NOT NULL,
  target_lang   TEXT NOT NULL,      -- 目标语言代码，如 ja / en
  text          TEXT NOT NULL,
  engine        TEXT NOT NULL,      -- system-translation / local-llm / manual
  engine_version TEXT,              -- 引擎升级后可识别旧译文需重翻
  edited_by_user INTEGER DEFAULT 0, -- 用户手动修正过则优先展示
  created_at    INTEGER,
  UNIQUE(segment_id, target_lang, engine_version)
);

-- 生词本（见 8.5）
CREATE TABLE vocab_items (
  id            TEXT PRIMARY KEY,
  lemma         TEXT NOT NULL,      -- 词形还原后的原形
  lang          TEXT NOT NULL,      -- 该词属于哪种语言
  surface_forms TEXT,               -- 见过的表面形式（buy/bought/buying）
  definition    TEXT,               -- 释义（端侧 LLM 生成或词典）
  example       TEXT,               -- 例句
  status        TEXT DEFAULT 'new', -- new / learning / known / ignored
  first_seen_at INTEGER,
  last_seen_at  INTEGER,
  seen_count    INTEGER DEFAULT 1,
  UNIQUE(lemma, lang)
);

-- 生词出现的上下文（一个词可能出现在多个句子里）
CREATE TABLE vocab_occurrences (
  id            TEXT PRIMARY KEY,
  vocab_id      TEXT NOT NULL,
  segment_id    TEXT NOT NULL,
  session_id    TEXT NOT NULL,
  context_text  TEXT,               -- 该词所在的原文句子
  created_at    INTEGER
);

-- 术语表（不翻译的人名 / 专有名词，见 7.4）
CREATE TABLE glossary_terms (
  id            TEXT PRIMARY KEY,
  term          TEXT NOT NULL,      -- 源语言中的词
  target_lang   TEXT,               -- NULL = 所有语言都不译
  replacement   TEXT,               -- 指定译法；NULL = 原样保留
  created_at    INTEGER
);

9.2 中文全文检索（FTS5）

项设计
索引类型SQLite FTS5（Full-Text Search 5）虚拟表
中文分词使用 trigram 分词器（按 3 字符滑窗切分）。它不依赖词典、天然支持中文子串匹配
已知限制trigram 要求查询串至少 3 个字符。少于 3 字（如「报销」以外的一字词）需回退到 LIKE 查询
同步方式用触发器（trigger）在 transcripts 增删改时同步 FTS 表
运行时校验App 启动时校验 FTS5 与 trigram 是否可用；不可用则降级为 LIKE，保证功能不缺失（见风险 R13）

9.3 点句回听（时间戳对齐）

检索命中后要能"跳回原声"，依赖三条链路严格对齐：

  1. 转写片段的 start_ms / end_ms 是相对会话起点的偏移
  2. 音频分片的 start_ms / end_ms 使用同一基准
  3. 回听时：由转写片段的时间区间定位到所属分片 → 打开该分片 → 定位到 (区间起点 − 分片起点) 处播放

若音频已被自动清理（超过保留期），转写文本仍保留，但回听按钮置灰并提示「音频已过期」。文本永久、音频有限是本项目明确的存储取舍。

10.3 关键接口（约定草案）

以下为模块边界的协议约定（Swift protocol），是后续编码的契约。实际命名可在实现时微调，但分层依赖方向不可变。

// 采集源：可替换。环境模式用麦克风直采，会议模式用系统内录（见 4.6）
enum CaptureSourceKind { case microphone, systemAudio }
enum AudioChannel { case ambient, me, them }   // 系统内录可区分「我」与「对方」

protocol CaptureSource: AnyObject {
    var kind: CaptureSourceKind { get }
    // 采集到的音频帧带上通道标记；麦克风直采恒为 .ambient
    var onFrame: ((AudioFrame, AudioChannel) -> Void)? { get }
    func start() throws
    func stop()
}

// 采集层：只管录，不感知上层；内部持有一个当前生效的 CaptureSource
protocol AudioCapturing: AnyObject {
    var state: CaptureState { get }
    var activeSource: CaptureSourceKind { get }
    var onSegment: ((AudioSegmentMeta) -> Void)? { get }   // 分片落盘完成
    var onGap: ((TimeRange) -> Void)? { get }              // 中断造成的空洞
    func start(using source: CaptureSourceKind) throws
    func stop()
}

// 增强层：双轨输出
protocol SpeechEnhancing {
    // 返回 (原始轨, 降噪轨)；降噪可被设置关闭，此时两路相同
    func process(_ frame: AudioFrame) -> (raw: AudioFrame, enhanced: AudioFrame)
    func segments() -> AsyncStream          // VAD 输出
}

// 识别层
protocol Transcribing {
    func realtime(_ segment: SpeechSegment) -> AsyncStream // 增量修正
    func finalize(_ range: TimeRange) async throws -> [TranscriptDraft]
}

// 说话人层
protocol Diarizing {
    func assign(_ drafts: [TranscriptDraft], in sessionId: String) async throws -> [TranscriptDraft]
}

// 存储层
protocol TranscriptStoring {
    func save(_ items: [TranscriptDraft], pass: PassKind) throws
    func search(_ query: String, limit: Int) throws -> [SearchHit]
}

// 翻译层：对外只暴露统一协议，便于将来替换实现（默认只有系统翻译实现）
protocol Translating {
    // 语言对是否可用；已下载/未下载/不支持
    func availability(from: String, to: String) -> LanguageStatus
    // 按需翻译；已缓存的段落直接返回，不重复请求
    func translate(segments: [TranscriptDraft],
                   to target: String,
                   progress: (Int, Int) -> Void) async throws -> [TranslationDraft]
    // 用户手动修正译文
    func override(segmentId: String, target: String, text: String) throws
}

// 学习层：生词判定（查表）与释义（端侧 LLM）分离
protocol VocabExtracting {
    // 纯查表 + 词形还原，不做生成
    func extract(from segments: [TranscriptDraft], lang: String) -> [VocabCandidate]
    // 生成式释义，可能失败，属于增强项
    func explain(_ item: VocabItem, context: String) async throws -> VocabExplanation
}

// 朗读与跟读
protocol SpeechRendering {
    func speak(_ text: String, lang: String, rate: Float)
    // 跟读：转写用户录音并与原文比对，返回文本层面准确度（非音素级评分）
    func scoreShadowing(reference: String, userAudio: URL, lang: String) async throws -> ShadowingScore
}

// 调度层：决定重任务时机
protocol TaskScheduling {
    func planFinalPass(sessionId: String)
    func requestBackgroundWindow()                          // BGProcessingTask
    func thermalStateChanged(_ state: ProcessInfo.ThermalState)
}

模式组成预估耗电适用

平衡档（默认）录音 + 实时稿（base）约 15%~25% / 小时（待实测）会议、访谈等需要当场看字

11.2 录音页设计要点

  • 状态必须一眼可辨：正在录 / 已降档（省电模式，转写暂停）/ 出现断口（有段落漏录）三种状态用颜色区分，避免用户以为一直在正常记录
  • 实时字幕区把"还在识别中"的片段做视觉弱化，明确传达"文字可能被修正"，避免用户觉得内容在乱跳
  • 不隐藏录音指示器带来的事实：页面上明确显示"正在录音"，与系统指示器相互印证
  • 模式必须显眼且不可含糊：环境模式 / 会议模式是两条互斥的采集路径（见 4.6）。会议模式无法"点一下就录"，必须由用户经系统录制入口选择本扩展，因此页面上要明确指引，并显示当前实际生效的采集源
  • 会议模式下要显示两路状态：我（麦克风）与对方（系统音频）是否都在正常采集 —— 任一路中断都要当场可见，否则事后发现只录到一半就来不及了

11.3 会话详情设计要点

  • 双稿可对照：默认展示终稿；可一键切到实时稿并排对比（用于评估质量，也是 A/B 测试降噪效果的界面）
  • 说话人着色：不同说话人用不同颜色标识（配合暗色主题克制取色），未命名显示「说话人 N」，点名即可命名
  • 点句回听：段落左侧时间戳可点击，跳转播放该段音频；音频已过期则置灰
  • 一键纠正：段落上可手动改说话人（"这段不是他"），改动反馈进声纹库
  • 断口与重叠透明化：断口以分隔线标注；疑似重叠说话的段落加标记
  • 语言切换就近放置：语言选择器固定在会话详情的顶部工具条（不藏在设置里），因为它是高频操作

11.4 说话人管理设计要点

  • 录入流程要短：录 10~30 秒 → 立即给出质量反馈（是否太短/太吵）→ 入库
  • 支持合并人物（同一人被建成两个身份时）与拆分（两个人被误合成一个）
  • 删除某人时须二次确认，并明确提示将同时删除其声纹特征

11.5 语言选择界面设计要点

要素设计

11.6 学习模式界面设计要点

学习模式的完整形态见 8.6，此处只补两条交互原则：

  • 音频是主角，文字是配角：学习模式的主操作必须是「再听一遍」，而不是「读文字」。复读按钮应是页面上最大、最易按的控件（可能是整屏点击）
  • 不打断思路：跟读、收藏生词、切语言都必须在一屏内完成，不跳页、不弹窗遮挡
设计提醒：这是本项目唯一一个「用户会长时间停留」的界面，也是唯一一个「单手操作 + 频繁点击」的界面。它的交互成本直接决定这个功能会不会被用起来 —— 一个跳三层的复读按钮等于没有。

翻译缓存Translation Cache已翻结果按（段落, 语言）存库，再次切换语言时直接命中
语言可用性Language Availability查询某语言对是否被支持、语言包是否已下载
双语对照Bilingual / Parallel Text原文与译文逐句并排呈现，是语言学习的标准材料形态
术语表Glossary指定某些词（人名、专有名词）不翻译或固定译法的对照表
逐段语言检测Per-Segment Language Detection对每个句子单独判定其语言，用于处理中英夹杂的对话
系统端侧语言模型System Language Model / Foundation ModelsiOS 26 内置的端侧大语言模型，可免费调用做生成式任务
文本转语音TTS (Text-to-Speech)把文字读出来
跟读Shadowing跟着原声复述，语言学习中训练听说的高频方法
音素级发音评分Phoneme-level Pronunciation Scoring对发音本身打分（本项目明确不做，只做内容准确度比对）
时间伸缩 / 变速不变调Time-Stretching / Pitch Preservation慢放音频时保持音高不变，是慢速复读不失真的前提
词形还原Lemmatization把 buy / bought / buying 归并为同一个词，避免生词本被同一词占满
分词Tokenization / Word Segmentation把连续文本切成词；中文无空格，必须专门分词
词频表Frequency Table / Word List按出现频率排序的词汇表，用于判断"是不是常见词"
生词本Vocabulary Book跨会话累积的个人生词集合
间隔重复SRS (Spaced Repetition System)按遗忘曲线安排复习的算法（本项目 v1 不做）
释义 / 讲解Definition / Explanation结合上下文说明词义与用法，由端侧 LLM 生成
采集源Capture Source音频数据的来源，本项目有麦克风直采与系统内录两种
系统内录System Audio Capture捕获设备上其他 App 播放出来的音频（而非它们采集的麦克风输入）
广播上传扩展Broadcast Upload ExtensionReplayKit 提供的独立 App 扩展，是 iOS 上实现系统内录的唯一合法途径
屏幕采集器RPScreenRecorder / RPSystemBroadcastPickerViewReplayKit 的录制对象与系统启动入口；后者是用户手动开启系统内录的入口
采样缓冲类型RPSampleBufferType (audioApp / audioMic)区分"其他 App 的音频输出"与"麦克风输入"两类采样
独占资源Exclusive Resource同一时刻只能被一个 App 持有的系统资源；麦克风即属此类，这是"无法录其他 App 麦克风输入"的根因
环境模式 / 会议模式Ambient Mode / Meeting Mode本项目两种互斥的录制模式，分别对应麦克风直采与系统内录
共享容器App Group Shared Container主 App 与扩展之间交换数据的共享目录，用于把扩展采到的音频交给主 App
单调时钟Monotonic Clock不受系统时间调整影响的计时基准，用于两路音频的时间戳对齐
