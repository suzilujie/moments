1. 平台约束类概念（Platform Constraints）

概念（中 / 英）定义来源与状态关联
静默开麦禁止
No Silent Mic Activation		 iOS 不允许 App 在无用户交互的情况下自行启动麦克风采集 设计阶段确认；已接受。直接决定了「随时能录」只能实现为「点一次开始后持续录」 全时录音
录音指示器
Recording Indicator		 只要有 App 在采集麦克风，系统就在灵动岛/状态栏显示指示点，锁屏亦有提示；App 层无 API 可隐藏 设计阶段确认；已接受。排除了「隐蔽采集」的产品定位，反过来成为「正在记录」的天然状态展示 合规提示
后台音频执行权
Background Audio Execution Right		 声明 UIBackgroundModes = audio 后，正在进行的音频采集/播放即构成合法的后台执行理由，锁屏不会挂起进程 设计阶段确认；采纳。比"播放静音 PCM 保活"更正当——本项目中录音本身就是保活来源，无需取巧手段 静默保活（被否）、中断恢复
静默保活
Silent Keep-Alive		 循环播放一段完全静音的音频，借助系统的"正在播放音频"状态换取后台执行权 既有项目（FloatingTicker）曾采用；本项目不采用，因为录音会话本身就是更正当的后台执行理由 后台音频执行权
蜂窝下载上限
Cellular Download Limit		 App Store 对超过 200 MB 的 App 要求用户必须连 Wi-Fi 才能下载安装 设计阶段确认；已规避。本项目模型体积远超此限，因此模型不打进 ipa 模型按需下载
低电量模式
Low Power Mode		 用户开启后系统限制后台活动与网络，可能导致后台转写被压制 设计阶段登记；待实测。对策是主动降档而非对抗系统 能耗档位、降档策略
热控降频
Thermal Throttling		 设备过热时系统主动降低 CPU/GPU 频率，持续推理会触发 设计阶段登记；待实测。监听 ProcessInfo.thermalState 并逐级降档 降档策略、能耗档位
麦克风独占
Exclusive Microphone Access		 麦克风是独占资源，同一时刻只有一个 App 能持有输入流；其他 App 采集到的音频数据对本 App 完全不可见 用户提出「录所有使用麦克风的语音」时核实；平台能力缺失。直接否掉了"录其他 App 麦克风输入"这一诉求，也决定了两种采集模式互斥 系统内录、环境模式/会议模式
系统内录可行性边界
System Audio Capture Boundary		 「录其他 App 播放出来的声音」可行（经 ReplayKit 广播扩展）；「录其他 App 的麦克风输入」不可行 用户需求澄清；前者 2026-09-22 确认纳入范围（M8）、后者排除。区分这两者是本次需求的关键 广播上传扩展
通话录音不可行
No Call Recording API		 iOS 不提供电话通话录音 API；声称能录电话的 App 均借助三方通话服务绕道 设计阶段核实；明确排除，并在非目标中写明。必须让用户知道这不是取舍而是能力缺失 合规提示
音频会话仲裁
Audio Session Arbitration		 多个 App 的音频会话由系统仲裁，且是双向的：我们不带混音选项会中断别人；别人不带混音选项也可能中断我们 M1 设计阶段核实；已接受。这决定了"共存不等于安全"，共存模式下仍必须保留完整的中断恢复与断口标注能力 音频会话策略、中断恢复

2. 音频采集与编码类概念

概念（中 / 英）定义来源与状态关联
全时录音
Always-On Recording		 用户手动点「开始」后，App 在前台/后台/锁屏三种状态持续录音，直到用户主动停止，不设时长上限 用户需求确认；已定方案。配两道保险：单次上限 12 小时、剩余磁盘 < 1 GB 自动停止 静默开麦禁止、后台音频执行权
采集参数标准
16 kHz / Mono / 16-bit		 语音识别的标准输入规格：采样率 16 kHz、单声道、16 位深度 设计阶段确定；已定。whisper.cpp 与 sherpa-onnx 均以此为基准，无需重采样 PCM 容量估算
分片落盘
Segment Rolling / Chunked Persistence		 录音按固定时长（60 秒）切成分片文件滚动写入，而非整段录完再写 设计阶段确定；已定。目的是把"崩溃/被杀"的损失限制在单个分片 原子重命名、时间轴断口
原子重命名
Atomic Rename		 先写入临时文件，完成后改名到正式文件名，避免产生"半截文件"被当成有效分片 设计阶段确定；已定 分片落盘
时间轴断口
Timeline Gap		 录音被中断后，两个分片的时间区间之间出现的空白 设计阶段引入；已定。核心原则是让漏录可见，而不是假装时间轴连续 中断恢复、分片落盘
双轨录制
Dual-Track Capture		 麦克风输入同时走两条处理链：原始轨（raw，不加工）与降噪轨（enhanced，经 GTCRN 处理） 用户确认；已定方案。关键澄清：双轨指处理链双路，不等于存两份——默认只持久化原始轨 降噪反噬、GTCRN
AAC 编码
AAC-LC (Advanced Audio Coding)		 系统原生的有损音频编码。16 kHz 单声道 32 kbps 下每小时约 14 MB，约为未压缩 PCM 的 1/8 设计阶段修正后选定；已定。原方案选 Opus，经核实编码路径不可靠而改为 AAC——Opus 在 Apple 音频栈中主要以解码形态存在，要保证编码可用就得引入第三方 libopus，为省几 MB 存储加一个 C 依赖不划算 Opus（已否）、容量估算修正
Opus 编码
Opus Codec		 专为语音优化的开源有损编码，压缩率高 原方案选定，已否决。原因：Apple 音频栈中其编码支持不确定（主要以解码形态服务 FaceTime / HLS 等场景）；保证可用需引入第三方依赖 AAC 编码
编码器启动延迟
Encoder Priming Delay		 有损编码器在每个文件开头引入的样本偏移（AAC 通常约两千余采样点） 设计阶段识别；已定对策。因每 60 秒切一个新文件，该偏移会累积成数十毫秒级跨片偏差 → 时间轴改用样本计数推导，不用墙钟时间相减 AAC 编码、时间轴推导
PCM 容量估算修正
PCM Size Correction		 16 kHz × 16 bit × 单声道 = 32 KB/s ≈ 110 MB/小时 前次方案沟通中误算为 68 MB/小时，设计阶段发现并修正；已更正。压缩后的结论不变 Opus 编码、自动清理
采集与转写解耦
Capture–Transcription Decoupling		 采集层不得依赖任何上层；两者之间用有界队列缓冲，队列满时丢转写任务而不丢音频 设计阶段确立为本项目最重要架构纪律；已定。与既有项目"行情自愈"经验同源 分层职责、能耗档位
采集源抽象
Capture Source Abstraction		 把「音频从哪来」抽象成可替换的接口，环境模式用麦克风直采、会议模式用系统内录，上层不感知差异 用户提出系统内录需求后引入；已定。是本项目能在不重写上层的前提下增加第二种采集源的前提 环境模式/会议模式
环境模式 / 会议模式
Ambient Mode / Meeting Mode		 两种互斥的录制模式：前者麦克风直采（轻量省电、可全时常开），后者系统内录（质量高但更重、需经系统入口手动启动） 用户需求澄清后确立；已定方案。不做"同时双采"，因为麦克风独占使同时采集不可靠；与其做一个不可靠的"同时"，不如做两个各自可靠的模式 麦克风独占、系统内录
广播上传扩展
Broadcast Upload Extension		 ReplayKit 提供的独立 App 扩展（继承 RPBroadcastSampleHandler），是 iOS 上实现系统内录的唯一合法途径 设计阶段选定；2026-09-22 确认纳入范围（M8）。内存限制极严，不能在其中跑推理，音频须经共享容器交给主 App 共享容器、系统内录
两路音频（我 / 对方）
Two-Channel Capture		 系统内录可拿到 audioApp（其他 App 的输出，即"对方"）与 audioMic（麦克风，即"我"）两类采样 设计阶段识别为系统内录的最大附加收益；已定。身份在数据层天然可辨，说话人分离的难度大幅下降（少一路聚类对象） 说话人分离、系统内录优势
数字原声优势
Digital Source Advantage		 系统内录拿到的是对方音频的数字原声：无环境噪声、无房间混响、无回声、无隔空衰减 设计阶段识别；已记录。对在线会议的转写与翻译质量是质变级提升，也是本项目翻译与语言学习价值的放大器 两路音频、端侧翻译质量上限
共享容器
App Group Shared Container		 主 App 与扩展之间交换数据的共享目录 设计阶段确定；已定。用于把扩展采到的音频交给主 App 处理（扩展内不能跑推理） 广播上传扩展
单调时钟对齐
Monotonic Clock Alignment		 两路音频使用同一单调时钟基准打时间戳，避免系统时间调整导致错位 设计阶段确定；已定。偏差超阈值时在时间轴上标注可信度下降，而不是假装对齐 两路音频
屏幕视频一律丢弃
Discard Screen Video		 系统内录路径必然经过屏幕录制通道，但本项目只保留音频，屏幕画面不落盘 设计阶段确认为硬约束；已定。既是隐私立场，也是降低审核风险与存储开销的必要做法 合规、广播上传扩展
音频会话策略：独占 vs 共存
Exclusive vs Coexistent Session		 两条互斥路线：独占（.record，录音干净但让其他 App 的音频停止）vs 共存（.playAndRecord + mixWithOthers，手机可正常用但会录到本机外放声） M1 设计阶段识别为关键取舍；已定：默认共存，另提供「高保真（独占）」开关。理由：核心承诺是"一直录"，若开启录音就让手机变砖，用户第二天就不会再打开 —— 录音再干净也没有意义 音频会话仲裁、会议模式
实时线程纪律
Real-time Thread Discipline		 音频采集回调运行在实时音频线程上，禁止在其中分配内存、加锁、做 I/O 或调用可能阻塞的 API M1 设计阶段确立为硬约束；已定。违反的后果不是报错，而是偶发丢帧与爆音（数据静默损坏），几乎无法事后定位 环形缓冲、采集与转写解耦
环形缓冲
Ring Buffer		 实时线程与后台线程之间传递音频的无锁缓冲结构（预分配，仅 memcpy + 原子指针更新） M1 设计阶段确定为实时线程纪律的落地手段；已定 实时线程纪律
录音内核状态机
Session State Machine		 idle → preparing → recording → interrupted → recovering → … → stopping → finalizing → idle 的单一权威状态来源 M1 设计阶段确定；已定。所有状态变更只经由一个串行执行体，UI 只作观察者；既有项目曾因"回调线程直接改状态"出过线程安全问题，这里从结构上避免 停滞看门狗、降档策略
停滞看门狗
Stall Watchdog		 独立于系统通知的健康检查：记录最后一帧到达时刻，超过 3 秒无帧即判定停滞并自愈 M1 设计阶段引入；已定。存在的理由是还有一类更危险的情形：系统不报任何错、音频却已经不来了。与既有项目"行情自愈"的看门狗思路同源 录音内核状态机、单调时钟对齐
孤儿分片
Orphan Segment		 音频文件已落盘、但数据库里没有记录的分片 M1 设计阶段确定；已定。启动时扫描音频目录补登记 —— 对应"先落文件再写 DB"的取舍：宁可丢元数据，不可丢音频 分片落盘、App 强杀恢复
App 强杀恢复
Crash Recovery		 录音开始时写"活跃会话"标记；启动时若发现标记仍在而实际未在录，即判定为异常终止并提供恢复入口 M1 设计阶段确定；已定。定位为无调试器环境下的关键诊断入口——没有实时崩溃日志可看，只能让 App 自己识别"我上次是异常死的" 录音内核状态机

3. 语音识别类概念（ASR）

概念（中 / 英）定义来源与状态关联
Whisper OpenAI 开源的语音识别模型，多语言、抗噪强。它是一个模型文件，不是应用 设计阶段选型；已定为识别引擎的基础 whisper.cpp
whisper.cpp Whisper 的 C/C++ 重写移植版，无 Python 依赖，可在 iOS 上通过 CoreML/Metal 加速运行 用户确认；已定为识别引擎 量化、ANE、两遍转写
批式 vs 流式
Batch vs Streaming		 Whisper 的输入是"一段完整音频"、输出是"一段完整文字"，属批式模型；不像流式模型那样逐字产出 设计阶段澄清；已接受。这是"实时字幕需要自己搭"的根本原因 滑窗自我修正
滑窗自我修正
Sliding Window Self-Correction		 边录边用"已积累的音频 + 滑窗重叠上下文"反复重解当前片段，输出覆盖式更新，实现准实时字幕 设计阶段确定；已定。已知现象：前几秒的字会被后续修正，不是 bug 批式 vs 流式、幻觉
两遍转写
Two-Pass Transcription		 同一段音频转两次：录音中用 base 出「实时稿」保证秒级可见；录音后/充电时用 small 出「终稿」保证准确 用户确认；已定方案。价值在于把"耗电"与"准确"解耦：白天可关实时转写换续航 能耗档位、模型选型
幻觉
Hallucination		 模型在无语音或极安静处凭空生成文字（如「谢谢观看」「字幕由 xx 提供」），是 Whisper 的已知缺陷 设计阶段登记；需对策：VAD 严格把关 + 高重复文本黑名单 + 无语音活动时输出空 VAD、两遍转写
量化
Quantization		 降低模型参数精度以缩小体积、加快推理，代价是极小的精度损失（如 q5 量化） 设计阶段选定；已定。base 由 142 MB 降至约 57 MB，small 由 466 MB 降至约 181 MB 模型选型、模型按需下载
神经引擎
ANE (Apple Neural Engine)		 Apple 芯片中专门执行神经网络推理的硬件单元，经 CoreML 调用 设计阶段选定为加速增益项；待验证。转换需在 macOS 上用 coremltools，存在失败可能，故不作为必需路径 CoreML、Metal
模型按需下载
On-Demand Model Download		 模型不打包进安装包，首次使用时从网络下载并校验（sha256），存放在 Application Support 设计阶段确定；已定。用于绕开 200 MB 蜂窝下载限制 蜂窝下载上限
SenseVoice 备选
SenseVoice (Fallback)		 sherpa-onnx 自带的中文更强、速度更快的离线识别模型，非自回归因而延迟更低 设计阶段记入备选；备而不用。因 sherpa-onnx 已在技术栈内，切换零增量成本 whisper.cpp、sherpa-onnx

4. 语音处理与说话人类概念

概念（中 / 英）定义来源与状态关联
sherpa-onnx 新一代 Kaldi（k2-fsa）团队的开源语音推理框架，一个库覆盖 ASR、VAD、说话人分离、语音增强、TTS 等能力，官方提供 iOS xcframework 与 SwiftUI 示例 设计阶段选定为语音处理层；已定。选它的核心收益是"三件事一个依赖" VAD、GTCRN、说话人分离
语音活动检测
VAD (Voice Activity Detection)		 逐帧判断音频中"此刻有没有人在说话"，用于切出语音段 设计阶段确定；已定。它是整个链路的闸门：只把语音送进转写与声纹，既省电又抑制幻觉 幻觉、说话人分离
GTCRN 语音增强
GTCRN Speech Enhancement		 sherpa-onnx 内置的降噪模型（Global Token Channel Attention Recurrent Network），用于压制背景噪声 用户要求"能去除噪音"；已定采用，构成双轨架构的降噪轨 双轨录制、降噪反噬
降噪反噬
Denoising Backfire		 降噪算法自身引入失真伪影（artifact / musical noise），抹掉识别模型所需的语音细节，导致字错误率不降反升 设计阶段识别为关键反直觉点；待 A/B 实测。因此"降噪"在本项目的定位是"可验证的选项"而非"无条件的改进"——这也是双轨架构存在的唯一理由 双轨录制、WER
字错误率
WER (Word Error Rate)		 识别准确率的核心评估指标，衡量识别文本与正确文本的差异比例 被选为降噪 A/B 对比的量化依据；待实测（M3 验收需产出对比报告） 降噪反噬
说话人分离
Speaker Diarization		 判断"哪一段是谁说的"，产出「时间段 → 说话人标签」的映射 用户要求；已定要自己做 声纹嵌入、聚类
说话人分离四步链路
Segmentation → Embedding → Clustering → Labeling		 ① 语音分割切出"可能是同一人"的小段 → ② 每段提取声纹向量 → ③ 向量聚类归组 → ④ 把标签回填到转写结果 设计阶段确定；已定。四步缺一不可 pyannote、声纹嵌入、聚类
语音分割
Speaker Segmentation（pyannote）		 把语音段进一步切成"同一个人在说"的连续片段，是分离链路的第 1 步 设计阶段选定 pyannote segmentation-3.0（ONNX）；已定 说话人分离四步链路
声纹嵌入
Speaker Embedding / Voiceprint		 把一段语音压缩成定长向量（如 512 维 float32），代表该说话人的音色特征，是"认人"的唯一依据 设计阶段选定 3D-Speaker / WeSpeaker；已定 声纹库、聚类
聚类
Clustering		 把相似的声纹向量自动归成一组，产出"说话人 A / B / C"的局部编号 设计阶段确定；已定。关键认知：聚类只能给出局部编号，不认识"张三李四" 声纹库、超长会话分块
声纹库
Speaker Profile Registry		 长期保存的声纹向量集合，用于把"说话人 3"识别为具体的人，实现跨录音认人 用户确认为必须能力；已定方案。每人保留多条向量（不同场景/设备/语速），比对时取最大相似度 声纹录入、相似度阈值
声纹录入
Enrollment		 主动录 10~30 秒语音把某人登记进声纹库，是冷启动阶段的必要手段 用户确认为必须能力；已定。另一条路径是"事后命名"（把已录制的说话人命名），免录入、越用越准 声纹库
相似度阈值
Similarity Threshold		 判定"是否同一个人"的余弦相似度分界线（初始取 0.7 量级） 设计阶段定为必须真机标定的参数；待标定。偏高→同一人被拆成多人；偏低→不同人被合并（后者体验更糟） 声纹库、余弦相似度
超长会话分块
Chunking		 把数小时的会话切成若干 10 分钟块独立处理 设计阶段确定；已定。原因：聚类是批式全局优化，一次处理数万段会内存耗尽 跨块身份对齐
跨块身份对齐
Speaker Linking		 用每块的簇质心（centroid）向量互相比对，把不同块里的"说话人 1"统一成同一身份 设计阶段确定；已定。关键：以向量对齐，而非依赖块内序号（序号在块之间无意义） 超长会话分块、声纹库
重叠说话
Overlapping Speech		 两人及以上同时说话的情形，会让说话人分割准确率显著下降 设计阶段登记为已知边界；接受降级。对策：标注「可能多人同时说话」而非假装正确；文字保留、归属置「未知」 说话人分离

5. 存储与检索类概念

概念（中 / 英）定义来源与状态关联
FTS5 全文索引
FTS5 (Full-Text Search 5)		 SQLite 的全文检索扩展（虚拟表），用于在大量转写文本中快速匹配关键词 设计阶段选定；已定 trigram 分词器、点句回听
trigram 分词器
Trigram Tokenizer		 按 3 个字符滑窗切词的 FTS5 分词器，不依赖词典，天然支持中文子串检索 设计阶段选定；已定。已知限制：查询串需 ≥ 3 字符，不足时回退 LIKE FTS5
点句回听
Timestamp Replay		 检索命中后点击句子即跳转到对应音频位置播放 设计阶段选定为核心价值功能；已定。依赖转写片段与音频分片使用同一时间基准 时间戳对齐、音频过期策略
音频过期策略
Audio Expiry Policy		 转写文本永久保留；音频按保留期（默认 7 天）滚动删除，过期后回听按钮置灰 设计阶段确定；已定。表述为「文本永久、音频有限」的明确存储取舍 自动清理、点句回听
时间字段本地化
Local-Time Convention		 所有时间字段存 Unix 毫秒（epoch ms，中性），展示时统一换算为用户本地时区（UTC+8） 沿用既有项目约定；已定。不存无时区字符串，避免时区偏移导致的判定错误 数据模型

6. 翻译类概念（Translation）

概念（中 / 英）定义来源与状态关联
翻译层
Translation Layer		 位于转写之后、独立负责多语言输出的模块 用户提出「转成不同语言输出」；已定方案（设计文档第 7 章） Whisper 翻译任务限制
Whisper 翻译任务的语言限制
Translate Task Limitation		 Whisper 内置的 translate 任务等价于「任意语言 → 英文」，不能翻成中文/日文等其他目标语言 设计阶段核实；已确认。这是"必须另设翻译层"的根本原因，也否掉了"靠识别引擎顺带完成翻译"的捷径 翻译层
按需翻译
On-Demand / Lazy Translation		 用户选择目标语言时才触发翻译，而非预先翻好所有语言；结果按 (段落, 语言) 缓存 用户确认；已定方案。收益：算力与存储不随语言数量膨胀，且换语言不需重跑识别 翻译缓存
翻译缓存
Translation Cache		 已翻结果入库，缓存键为 (segment_id, target_lang, engine_version) 设计阶段确定；已定。带引擎版本是为了引擎升级后能识别出旧译文可重翻 按需翻译
语言可用性
Language Availability		 查询某语言对是否被系统支持、其语言包是否已下载 设计阶段确定为前置校验；已定。不可用语言必须明确提示并引导下载，不得静默失败 端侧翻译质量边界
系统端侧语言模型
System Language Model / Foundation Models		 iOS 26 内置的端侧大语言模型，可免费调用，无需下载模型文件 设计阶段选定；采用。用于生成式任务（生词释义、句子讲解），不用于批量翻译（速度慢、输出不完全可复现） 生词释义
双语对照
Bilingual / Parallel Text		 原文与译文逐句并排呈现 设计阶段确定为默认呈现方式；已定。理由有二：端侧翻译质量有限，原文必须可见；且用户要学语言，看原文本身就是目的 端侧翻译质量边界
术语表
Glossary		 指定某些词（人名、专有名词）不翻译或使用固定译法的对照表 设计阶段提出；待用户确认（Q12）。端侧翻译对人名地名的处理尤其不可靠 双语对照
逐段语言检测
Per-Segment Language Detection		 对每个句子单独判定其语言，而非给整段录音强行贴一个语言标签 设计阶段确定；已定。使中英夹杂的对话能被正确处理，并能自动筛出"哪几句是外语" 翻译层、学习材料筛选
可插拔翻译接口
Pluggable Translation		 翻译层对外只暴露统一协议，云端实现作为预留选项存在但默认关闭 设计阶段确定；已定。目的是让"是否上云"这个决定可以将来再改，而不必重写架构 翻译层
端侧翻译质量上限
On-Device Translation Quality Ceiling		 受模型体积限制，离线翻译在口语、俚语、方言、长难句、专业术语、人名地名上明显失真，属必然结果而非缺陷 设计阶段确立为必须向用户诚实告知的平台事实；已接受。对策是"原文永远可见、译文可修正"，而非宣称准确 双语对照、术语表

7. 语言学习类概念（Language Learning）

概念（中 / 英）定义来源与状态关联
学习材料化
Learning Materialization		 把用户自己录到的真实语音转成学习材料（逐句对照 + 可回听 + 生词沉淀），不做语言课程 用户提出「能帮助我学习语言」；已定立场。真实语料是教材买不到的，而它恰好每天都在产生 学习闭环
先天句级对齐
Inherent Sentence Alignment		 VAD 切出的语音段本身就是句级单位，原文/译文/音频三者共用同一个 segment_id，因此「对齐」在数据模型成立时就自动完成 设计阶段识别为本项目的先天优势；已定。跨语言句对齐通常需要专门算法，这里天然省掉 说话人分离四步链路、双语对照
三档显示模式
Three Display Modes		 原文 / 译文 / 双语对照，可在界面上一键切换 设计阶段确定；已定。分别服务于"复习原话""快速理解""语言学习"三种意图 双语对照、学习模式
变速不变调
Time-Stretching / Pitch Preservation		 慢放音频时保持音高不变，即时间伸缩而非简单降采样 设计阶段确定；已定。必须——简单降速会让人声变调，反而更听不懂，失去学习价值 慢速播放
单句循环
AB Repeat		 反复播放同一句或指定区间，是语言学习中最高频的操作 设计阶段确定；已定，并要求一步可达（交互成本直接决定功能是否被用起来） 学习闭环、学习模式
跟读比对
Shadowing Comparison		 录下用户跟读 → 用已有 whisper 转写 → 与原文比对，给出内容准确度 设计阶段确定；已定。零新增依赖（复用识别引擎） 发音评分（明确不做）
音素级发音评分
Phoneme-level Pronunciation Scoring		 对发音本身打分，需音素对齐与韵律分析 设计阶段明确排除；不做。UI 文案必须避免让用户误以为跟读比对是发音打分 跟读比对
系统 TTS 朗读
Speech Synthesis (TTS)		 用系统 AVSpeechSynthesizer 朗读原文或译文，端侧、免费、多语言、语速可调 设计阶段选定；已定。用途：听目标语言标准发音、还原听不清的句子、整篇泛听。不替代原声回听（原声练真实听力，TTS 练清晰输入） 学习闭环
查表式生词判定
Frequency-Table-Based Vocab Detection		 用词频表（如高频 5000 词表）+ 用户水平档来划分数线，超出即标为生词 设计阶段确定；已定。明确不使用 LLM 判断生词——这是确定性问题，查表更快更稳可复现 词形还原、生词本
词形还原
Lemmatization		 把 buy / bought / buying 归并为同一个词 设计阶段确定为必需步骤；已定。不做这一步，同一个词会被算成三个生词，生词本会迅速失去意义 查表式生词判定
分词
Tokenization / Word Segmentation		 把连续文本切成词。中文无空格，必须专门分词 设计阶段确定；已定。英文按空格，中文用系统分词能力 查表式生词判定
生词本
Vocabulary Book		 跨会话累积的个人生词集合，含词形、释义、出现次数、来源句子、可回听片段 用户要求「帮助学习语言」的核心落点；已定方案。支持手动增删与自定义词表（误判必须可纠正） 生词释义、导出
学习模式
Study Mode		 会话详情页的一个开关，切换后界面重组为逐句卡片视图：原文 → 译文 → 点听 → 慢速 → 生词高亮 设计阶段确定；已定。交互原则：音频是主角、文字是配角；复读/收藏/切语言必须一屏内一步可达 单句循环、学习闭环
学习闭环
Learning Loop（听—看—复读—收词）		 一次完整的学习动作：听原声 → 看对照 → 复读跟读 → 收藏生词 设计阶段确立为 M6 的验收标准；已定。意义在于把"功能清单"换成"一条能真正走通的路径" 学习模式、生词本
间隔重复
SRS (Spaced Repetition System)		 按遗忘曲线安排复习的算法（如 SM-2 / FSRS） 设计阶段明确推迟；v1 不做，只做生词本 + 手动标记已掌握 生词本

9. 被否方案与拒绝理由（Rejected Options）

记录"为什么不这么做"，避免后续重复讨论。

被否方案拒绝理由
Apple 原生 Speech 作为唯一引擎无说话人分离能力、有调用限流、精度一般；且需额外申请语音识别权限
云端 ASR（Whisper API / 讯飞 / 阿里云）与"纯离线、音频不出手机"的定位冲突，且有按分钟计费与联网依赖
跨 Apple 设备组网采集第三方 App 无法读取其他设备的麦克风流；只能各录各的再按时间戳对齐，而时钟漂移难以做准
只做局部编号、不上声纹库无法跨录音认人，体验上限低
只标记「换人」不编号多人对话可读性差
降噪轨也持久化存盘降噪轨可由原始轨随时重算（GTCRN 很快），存两份是纯浪费存储
模型打进 ipa远超 200 MB 蜂窝下载限制，部分用户无法安装
仅用系统级语音处理链做降噪会改变原始录音数据、且不可对照，无法验证降噪是否反噬识别率
全部用 sherpa-onnx 的 Whisper（省掉 whisper.cpp）whisper.cpp 的流式滑窗示例更成熟、CoreML/ANE 路径更成熟；保留为后续可评估项
SwiftData / Core Data 作为主存储FTS5 全文检索支持不便，而检索是本项目的核心价值
TestFlight 分发既有项目已验证后放弃，改用 Ad Hoc
靠 Whisper 的 translate 任务实现多语言输出该任务只能翻成英文，无法输出中文/日文等目标语言
云端翻译 API（DeepL / Google / LLM）与"纯离线、文本不出手机"的核心定位冲突，且有费用与联网依赖
专用 NMT 模型（OPUS-MT / NLLB 蒸馏）语言对零散需分别维护；质量不如系统翻译框架，且属于"自己维护一份比不上系统的翻译"
本地小 LLM 做翻译（Qwen 0.6B~1.7B GGUF）质量最好但体积约 400 MB~1.1 GB、速度慢、耗电高。列为升级路径而非首选
让 LLM 判断"哪些词是生词"这是确定性问题，查词频表更快更稳更可复现，且零能耗。LLM 应只用于释义与讲解
预先把所有语言都翻好用户实际只看一两种语言，预翻 N 种语言等于 N 倍算力与存储浪费
实时同声传译（边录边译）能耗与延迟不可接受；且实时稿本身还在被滑窗不断修正，翻译一个还在变的文本会让字幕乱跳
跟读做音素级发音评分需音素对齐与韵律分析，属另一专业领域。只做文本层面内容准确度比对
SRS 间隔重复算法（v1）先做生词本 + 手动标记已掌握，算法列入 v2 评估，避免首版复杂度失控
完整语言课程 / 分级课程 / 题库那是教科书与专门学习 App 的领域；本项目只做"把真实录音变成学习材料"这一件事
录其他 App 正在使用的麦克风输入平台能力缺失，不可能：麦克风是独占资源，其他 App 的输入数据对本 App 不可见，iOS 无此 API
录电话通话平台能力缺失，不可能：iOS 不提供通话录音 API
同时使用麦克风直采 + 系统内录（双采并行）麦克风独占导致并行不可靠，且会产生回声与重复录制；改为两个互斥模式
只用系统内录做全时环境录音需经系统录制入口手动启动、有屏幕录制指示、耗电发热高，作为"随身全时录音"过重
保存屏幕画面本项目只需音频；保存屏幕既无必要，又抬高隐私与审核风险
用 Opus 作为落盘编码Apple 音频栈中 Opus 的编码路径不确定，保证可用需引入第三方 libopus；AAC 系统原生、体积相当、零依赖
在实时音频线程内做编码 / 加锁 / I-O会导致偶发丢帧与爆音（数据静默损坏），且几乎无法事后定位；改为预分配环形缓冲 + 后台队列
以「独占会话」为默认录音虽干净，但会让用户一整天不能听音乐看视频；对"全时录音"是灾难级体验，故降级为可选开关
用墙钟时间推导分片时间轴编码器启动延迟会让偏差逐片累积；改用样本计数推导
